# Radxa camera image: clean build from the official image (2026-10-27)

Why: the first camera had been assembled by hand on a single SD card (09-17…10-20), and some files existed only on the
board; cameras have to be moved to other networks and new ones built from scratch. From now on the camera is reproducible from the repository:
**official Radxa image + `image/radxa-zero3/provision.sh`**. Camera internals and pitfalls —
[radxa-zero3.md](radxa-zero3.md), the still service — [cam-still.md](cam-still.md).

**Status: the kit is written but has not been run on a board.** `flash-sd.ps1` was verified on 2026-10-28 on the
second camera's card (64 GB): 8 074 662 912 bytes in 309 s (~25 MB/s), read-back matched, partitions
16 MB / 300 MB / 7.4 GB. Checked on the PC only: `bash -n`, no CRLF, `push.ps1` parses in PowerShell 5.1, password
quoting in the remote script (byte by byte). The first run will be on the second board, following the checklist below.

## What was found on the current camera (ssh survey 2026-10-27, read-only)

| What | Current state | Risk when moving / cloning | Decision in the kit |
|---|---|---|---|
| Camera address in the client application | the client stores it by IP | a different network means a different address | **stays as is** (decision 2026-10-28): at the new site the IP is entered into the client again; find it by the camera's name (mDNS) or by the lease in the router. Better to pin the lease in DHCP |
| Camera hostname | all are `radxa-cam` (a fresh image has `radxa-zero3`) | several cameras on one network: avahi renames the second one, they cannot be told apart by name | each gets its own: by default `radxa-cam-<last 6 characters of the SoC serial>`, or `-Hostname` |
| mDNS returns IPv6 | avahi publishes AAAA `fe80::…`, the services listen on `0.0.0.0` only | Windows tries IPv6 first and gets refused: **2.2 s** for every new connection by name versus 0.08 s by address (measured 2026-10-27) | avahi `use-ipv6=no` — the name is then usable at least for discovery and ssh |
| Password of `radxa` | set by hand, not recorded anywhere | nothing can be fixed at a remote site | new password during provisioning (`push.ps1`), kept by the owner of the installation |
| ssh login | one key `radxa_cam` (ours), password login — Debian default (allowed) | — | `push.ps1` installs the key; the password remains a fallback login |
| MAC | `addr_assign_type` 0 — U-Boot derives it from the SoC serial | the second board will have its own, DHCP will not confuse them | nothing |
| ssh host keys, `machine-id` | unique per installation | when a card is cloned, two cameras share them | no cloning: each board is installed from the official image, keys and id are generated by rsdk's first boot |
| Fallback address | `169.254.176.50/16` in the NM profile alongside DHCP | identical on all cameras — address conflict on a shared network | kept, but unique per camera: `169.254.176.N`, N is asked by `push.ps1` (first camera 50, second 51, …; decision 2026-10-28) |
| Clock | `systemd-timesyncd`, Debian pool, UTC | without internet the time continues from the last saved value — affects only log timestamps | nothing |
| Logs | `/var/log/journal` 458 MB with no limit; `cam-blackbox.log` 382 MB in 40 days, no rotation | over years — until the card is full | `journald` ≤ 300 MB, `logrotate` for the black box (14 days, ≤ 50 MB) |
| Unneeded services | `samba-ad-dc`, `sddm`, `bluetooth`, `cups`, timers `apt-daily*`, `fwupd-refresh`; `rsetup-aic8800-reset@ttyS1` fails | automatic updates may bring a new kernel and bring back the RGA pitfalls | disabled; kernel, U-Boot, mpp, rga, rkaiq — `apt-mark hold` |
| Files that existed only on the board | `cam-blackbox`, `cam-modes.conf`, `mediamtx.yml`, units `mediamtx` / `cam-panel` / `cam-blackbox`, watchdog `10-watchdog.conf` | would be lost together with the card | moved to `image/radxa-zero3/rootfs` |
| `cam-probe-modes` | pins the sensor mode via `media-ctl` and **overwrites** the tuned `cam-modes.conf` | exactly pitfall 2 ([radxa-zero3.md](radxa-zero3.md)) | not installed in the image, kept in `reference/` |
| Service versions | on the board: `cam-still` 2 and `cam-panel` without the focus button | — | the repository versions are installed (cam-still 3, panel with the "Focus" button) |
| `mediamtx` | v1.21.0, unit without restart limits | — | same binary (sha256 is checked), unit with `StartLimit*`, `TimeoutStopSec=15` |

Snapshot of the board as of 2026-10-27 — `image/radxa-zero3/reference/`: package list (`dpkg-2026-10-27.txt`) and
sha256 of the files in `/usr/local` (`sha256-2026-10-27.txt`). The base image of that camera is rsdk-b1 of 15.07.2025,
the same one used now.

## The `image/radxa-zero3` kit

| File | What |
|---|---|
| `flash-sd.ps1`, `flash_sd.py` | on the PC: official image to the card — sha256 of the file, disk check (USB/SD only, not the system disk, ≤ 256 GB), wipe, `.xz` decompressed straight onto the card, read-back and sha256 comparison; requests administrator rights itself (UAC) |
| `push.ps1` | on the PC: uploads the key (the only ssh password prompt), assembles the kit in `%TEMP%\cam-image`, copies it to the board, runs `provision.sh` under sudo; `-Reboot` — reboot at the end |
| `provision.sh` | on the board, as root: checks the kit and the board, packages + `hold`, MediaMTX v1.21.0 (sha256 of the archive and the binary), service files, overlays `radxa-camera-8m` and `poe-hat`, hostname, avahi, NM profile `cam-eth`, password and key, services. Safe to re-run |
| `rootfs/` | files as on the board, installed at their paths (`/usr/local/bin` — 755, everything else — 644) |
| `reference/` | snapshot of the first camera, not part of the image |

Plus from `node/`: `cam-panel`, `cam-pipeline`, `cam-still`, `cam-still.service`, `cam-stream.conf`.

The network is changed **without reconnecting**: the profile is edited in place and takes effect after a reboot, so
the provisioning ssh session is not dropped. The stream (`mediamtx`) does not start at boot, as before:
`disable_service mediamtx` in `/config/config.txt` and the unit disabled.

## Procedure

### Second camera (here, from scratch)

1. Download `radxa-zero3_bookworm_kde_b1.output_512.img.xz` (1.45 GB) from
   [radxa-build/radxa-zero3, release rsdk-b1](https://github.com/radxa-build/radxa-zero3/releases/tag/rsdk-b1), verify
   sha256 `47b70ec81377f618505951fc9b4c40784e983c7fdff9706fdf79c13b6cd20730`, write it to the card — disk number
   from `Get-Disk`:

   ```bash
   powershell -File image/radxa-zero3/flash-sd.ps1 -DiskNumber <N> -Image $env:USERPROFILE/Downloads/radxa/radxa-zero3_bookworm_kde_b1.output_512.img.xz
   ```
2. Insert the card, cable to a network with DHCP and internet, power — **only one source** (PoE HAT or USB-C,
   pitfall 8). rsdk's first boot expands the partition and generates the keys — a couple of minutes.
3. Find the board: `radxa-zero3.local` or the lease in the router.
4. From the PC (a terminal; passwords have to be typed), in the repository root:

   ```bash
   powershell -File image/radxa-zero3/push.ps1 -CamHost radxa-zero3.local -Reboot
   ```

   The questions come in this order, all before the first contact with the board except the last one:
   1. N of the fallback address `169.254.176.N` (first camera 50, second 51, …);
   2. the current password of `radxa` — on a fresh image it is `radxa`;
   3. the new password, twice — make one up and hand it to the owner of the installation;
   4. ssh's own prompt `radxa@…'s password:` — again the **current** one (`radxa`): this installs the key, everything
      after that uses the key.

   The camera gets its own hostname
   (`radxa-cam-<serial>`, the `hostname:` line in the output); if there are several fresh boards on the network, pass
   `-CamHost` as the address from the lease, not `radxa-zero3.local`.
5. Run the checklist below; enter the camera's IP in the client application.

### First camera (before shipping)

1. Take a full copy of the current card (card reader, Win32 Disk Imager → `.img`) — a fallback in case the new one
   does not come up.
2. Reflash it with the same procedure as the second one. At the new site — enter the IP from the lease into the
   client application.
3. **The camera model (distortion) and any camera-dependent calibrations of the client are tied to the camera itself,
   its lens and its mounting**, not to the image: moving the camera means redoing them — distortion calibration and
   whatever calibrations the client builds on top of the camera (for example, a mapping from the camera image to
   the coordinates of the observed scene and the checks that rely on it).

### Client application

The client stores the camera's IP address, as before; nothing changes in code. There may be several cameras on one
network, each client uses its own camera by its IP. At a new site or after the lease changes — update the IP in the
client (for a client that moves together with the camera — on its own PC). The host scripts (`host/*`) take the
address from `RADXA_HOST`.

Finding the IP: `Resolve-DnsName <name>.local` from the PC (Windows resolves `.local` itself unless the firewall
blocks UDP 5353; here it works with the "Public" network profile), the lease in the router, or `ip -br addr` on the
board.

## Checklist after provisioning (on every board)

Below, `<name>` is the camera's hostname from the `provision.sh` output, `<IP>` is its address.

1. `ssh -i ~/.ssh/radxa_cam radxa@<IP>` — key login; `sudo -v` — with the new password; `hostname` — its own name.
2. From the PC: `Resolve-DnsName <name>.local` — an A record (IPv4) only, the same `<IP>`;
   `http://<name>.local:8081/status` — the first request **< 0.3 s** (was 2.2), `service` = `cam-still 3`.
3. `dmesg | grep -c rga` = 5; `/dev/video0` and `/dev/video1` exist (camera overlay).
4. Panel `http://<IP>:8080/`: start the stream, `http://<IP>:8889/cam` shows the picture, 19 fps; the "Focus" button
   opens `:8081/focus`.
5. A still from the client application — 16 frames, timing
   as in [cam-still.md](cam-still.md), "Deployed".
6. Reboot: everything above comes up by itself, `mediamtx` does not; `systemctl --failed` is empty.
7. Two cameras on one network: each has its own name and address, both respond, the client's stills come from the
   camera whose IP it has configured.
8. Direct cable to a PC without DHCP — the camera responds on its `169.254.176.N`. **Not tested on the first camera
   either**; if NM with an infinite DHCP wait (`ipv4.dhcp-timeout`) does not bring up the static address — document it
   here.
9. Network without internet (unplug the gateway): the camera and the client work; the clock runs from the last saved
   time.
